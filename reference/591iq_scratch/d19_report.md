# 写实记录详情越权与身份字段过宽（客户端已拦，请服务端修）

## 现象一：`queryRecord` 不校验记录归属

`POST /record/queryRecord`，载荷 `{"id":"<recordId>"}`。

服务端**只按 id 返回，不校验这条记录是否属于当前登录者**。前端之所以安全，
是因为它只能点开「自己的」记录、id 来自列表行；但接口本身对任意 id 都返回。

详情返回 27 个顶层键，其中 `userInf` 有 **51 个字段**，含：

| 字段 | 内容 |
|---|---|
| `identityCard` / `idNumber` | 身份证号、证件号 |
| `unifiedExaminationNumber` | 考号 |
| `birthday` | 出生日期 |
| `politicalStatus` | 政治面貌 |
| `letter` | 家庭住址 |
| `phoneNumber` | 手机号 |
| `userHeadImage` / `headImg` / `enrollmentPicUrl` | 照片 |
| `seatNum` / `cadres` | 座位号、班级干部 |

## 复现步骤

1. 用学生账号正常登录，取到 AccessToken
2. 先 `POST /record/queryRecordList`（`type=2` 班级 / `type=3` 学校）拿到任意
   班内或校内的 `recordContent.id`（列表行里就有，无需额外权限）
3. `POST /record/queryRecord`，body `{"data":{"id":"<上一步拿到的 id>"}}`
4. 响应 `code=0`，返回该记录完整内容 + 上述 51 字段的**作者**信息

## 现象二：`queryRecordList` 的 `type` 存在无过滤兜底分支

`POST /record/queryRecordList`，`type` 取值：

| type | 语义 | 实测条数 |
|---|---|---|
| `1` | 我的 | 20 |
| `2` | 班级 | 281 |
| `3` | 学校 | 146,020 |
| `4` | 年段 | 12,139 |
| `""` / `0` / `5` / 任意非法值 | **后端兜底分支，不做任何范围过滤** | **146,020** |

前四个对应学生端的 4 个 tab。**其余取值服务端不报错、不按默认值处理，而是走
兜底分支返回与「学校」同量级的全量数据**，且每行带作者姓名与班级。
前端不存在这个入口，属于超出界面设计的范围扩大。

## 影响

- 任何学生账号都能读到**同校任意其他学生**的记录正文，以及该生的
  身份证号、考号、政治面貌、家庭住址、照片等敏感个人信息（被涉及者为未成年人）
- 组合两个现象：列表可拿他人 id → 详情可拿他人完整身份信息，**无需任何特殊权限**
- 兜底分支让「按 tab 限定范围」这个隐含前提失效，客户端若依赖它做访问控制会漏

## 建议修复

1. `queryRecord` 校验 `id` 所属学生与 token 解析出的 `userId` 一致；
   不一致时返回权限错误码而非数据（教师端查看另走带角色校验的端点）
2. `queryRecordList` 对非法 `type` 返回参数校验错误（如 `999997`），
   不要静默走兜底分支
3. 详情响应按角色裁剪 `userInf`：学生本人只需 `userId`/`userName`/`className`；
   身份证号、考号、住址、政治面貌等不应出现在学生端详情里
4. 列表响应同样裁剪 `userInf`（当前每行都带作者信息）

## 已在客户端做的缓解（不替代服务端修复）

- 自动化工具已拦截：非法 `type_` 直接抛错（需显式 `unsafeScope=True` 才放行
  并留 WARNING 日志）；`queryRecord` 比对返回的 `userInf.userId` 与登录者，
  不一致就拒绝（需显式 `allowOther=True`），并把 `userInf` 默认收敛到 10 字段白名单
- 这只是客户端规避，**任何直接发 HTTP 的调用方依然可以拿到全量数据**，
  所以服务端侧仍需修复

## 补充

- 本工单不含任何真实姓名、学号、身份证号、考号、住址与凭据
- 现象一、二均多次实测确认，非推测
