主题两个检索接口在学生角色下可返回超出界面设计的范围与敏感度

一、摘要

在开发针对新壹我（天蛙）综合素质评价系统（www.591iq.cn）的自动化工具并进行自测的过程中，发现两处仅凭普通学生账号凭据即可调用、且返回范围或敏感程度超出学生端界面设计的检索接口。

被涉及的数据主体为在读未成年人，其中一处可直接返回姓名、班级，以及身份证号、考号、政治面貌、家庭住址、证件照等敏感字段。

本通知仅陈述风险并附修复建议，不含任何真实学生信息样本，不含任何访问凭据。

二、风险定级

项目评价
风险等级高
影响对象全校在读学生（未成年人）个人信息
触发条件任意一个正常取得的学生账号凭据，无需管理员或教师权限
可否批量获取可以（无频率限制、无单次返回上限、支持分页取全量）
是否需要认证需要，但学生角色即可

三、问题详述

问题一 · 人员检索接口未按角色限制，返回他人敏感身份信息

端点

GET https://service.591iq.cn/search/search

请求参数

{"type": "2", "content": "<姓名片段>", "pageRowBounds": {"offset": 0, "limit": 10}}

鉴权：仅需在请求头携带 AccessToken，学生角色凭据即可调用。

实测情况

操作结果
content 填单个汉字（如姓氏）totalResult 即达上千（实测 2324）
分别以多个常用汉字检索、按 userId 去重合并可枚举全校人员规模（此前实测约 2.8 万人量级）
返回的人员对象字段数约 51 个字段

返回字段中包含的敏感项（仅列字段名称，不含任何真实值）：

identityCard（身份证号）、idNumber（证件号）、unifiedExaminationNumber（考号）、birthday（出生日期）、politicalStatus（政治面貌）、letter（家庭住址）、phoneNumber、qq、enrollmentPicUrl / userHeadImage（证件照）、cadres（班级干部）、seatNum（座位号）等。

问题定性：学生角色本应只能查看与其本人相关的检索结果，实际可获得全校人员的上述字段。检索结果未随用户权限降级。

问题二 · 记录列表接口对非法 type 值不校验，静默返回全量数据

端点

POST https://service.591iq.cn/record/queryRecordList

请求参数

{"type": "<任意值>", "recordType": "", "labelId": "", "offset": 0, "limit": 10}

鉴权：同上，学生角色凭据即可调用。

前端对照：学生端界面只有 4 个范围选项：

type界面上的范围名称
1我的
2班级
3学校
4年段

实测情况

type 取值前端是否有对应入口返回总条数
"1"有（我的）18
"2"有（班级）281
"3"有（学校）146,020
"4"有（年段）12,139
""（空串）无146,020
"0"无146,020
"5"无146,020
"9"无146,020
"abc"（任意非法值）无146,020

问题定性

对非法 type 不返回参数校验错误，而是静默进入一个不做任何范围过滤的兜底分支； 该分支返回的数据量与「学校」范围同量级（146,020 条），并包含历年毕业届记录； 该分支前端无任何对应入口，属接口层的能力扩大； 返回的每一行均含 recordContent.userInf（作者的 userId / userName / className / schId），以及一个 32 位十六进制的记录 id，可用于后续调取该条记录的详情； 接口无频率限制、无单次返回条数上限，可分页取全量。

附带说明（另有一项，不在本单范围）

记录详情接口 POST /record/queryRecord 不校验记录归属，传入他人的记录 id 即返回该条记录的完整内容及作者身份字段。因该项不属于检索接口，本单暂不列入，可按需另附。

四、影响分析

越权读取未成年人个人信息。 任意学生账号即可取得全校学生的姓名与班级，以及身份证号、考号、政治面貌、住址、证件照等敏感字段。此类主体为未成年人，属个人敏感信息中风险最高的一档。 可批量、可重复。 两处接口均无频率限制与返回上限，实际可形成全校规模的个人信息副本。 信任边界被绕过。 调用方若依赖 type 参数做访问范围控制（一个看似合理的假设），非法取值即可使其完全失效。

五、建议修复方案

针对问题一

按 AccessToken 解析出的角色限定 type=2 分支——学生角色不应返回全校人员目录； 若业务确需同名检索，建议仅返回最小必要字段（如 userId、userName、className），identityCard、idNumber、politicalStatus、letter、照片类字段对非管理员角色一律不返回； 检索结果按当前用户的可见范围过滤，而非返回全量后交由前端处理。

针对问题二

对 type 做枚举校验，非法值返回参数错误（与系统现有 999997 参数校验失败 一致即可），不要静默落入兜底分支； 确认该兜底分支是否确有必要保留；若无必要，建议直接移除； 返回的每行 recordContent.userInf 中，作者信息同样应按角色裁剪。

通用建议

为列表类接口补充分页上限与频率限制； 对涉及身份证号、考号的字段增加按角色的服务端裁剪，而非仅在前端隐藏。

参考实现（我方工具侧已实现的客户端拦截）

我方已在自动化工具中实现对应的客户端拦截，可作为服务端实现的对照：

  • type 仅放行前端 4 个合法取值，非法值直接拒绝且不发出请求；
  • 记录详情比对返回的作者 ID 与当前登录者，不一致即拒绝；
  • 人员/作者身份字段默认收敛为白名单中的最小集合。

    ⚠️ 请注意：客户端拦截只防误用，不构成安全边界。 绕过该工具直接发送 HTTP 请求，依然可以取得全量数据。真正的修复必须在服务端完成。

    六、我方已采取的自我约束

    发现后立即停止使用上述两处能力，相关自动化代码已整体移除，且未保留任何绕过开关（不设环境变量旁路）； 未批量留存任何他人数据，全部数据仅在本地临时目录用于验证，并已清理； 本通知及所附证据中不含任何真实姓名、学号、身份证号、考号、住址与访问凭据； 已建立持续集成闸门，确保相关能力不会被后续版本重新引入。
